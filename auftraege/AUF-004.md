# AUF-004 — Datenmodell und Migration für mehrere Beschäftigungen

## Auftrag

Baue Datenmodell und Persistenz so um, dass die App **mehrere Beschäftigungen**
tragen kann, und migriere die vorhandenen Daten verlustfrei auf die erste davon —
**ohne** eine einzige neue Bedienmöglichkeit in der Oberfläche.

## Warum das gebraucht wird

Klarzeit kennt heute genau **eine** Beschäftigung, und zwar im Datenmodell, nicht nur
in der Oberfläche: ein einziges `Employment`-Objekt unter dem Preferences-Schlüssel
`employment` (`src/db/employment.ts:11`), Zeiteinträge ohne jede Zuordnung
(`src/domain/types.ts:14`), eine gemeinsame Urlaubsliste, eine einzige laufende
Erfassung. Wer zwei Arbeitsverhältnisse hat (Hauptjob + Minijob), bekommt deren
Stunden in einen Topf: das Ist beider Jobs steht gegen das Soll **eines** Vertrags.

Dies ist der erste von fünf Aufträgen. Er ist der riskanteste, weil er **echte
Nutzerdaten auf einem Gerät migriert** — deshalb steht er allein und ohne Oberfläche.
Die Rechenlogik wird dabei **nicht angefasst**.

## Gegenstand

| | |
|---|---|
| Werk(e) | `src/domain/types.ts`, `src/domain/employment.ts`, `src/db/db.ts`, `src/db/employment.ts`, `src/db/running.ts`, `src/db/entries.ts` |
| Stellen | die dort genannten Typen und Zugriffsfunktionen; dazu ein neuer Test je Migrationsweg |
| Material im Arbeitsort | `src/` (vollständig), `node_modules/` (als Kopie — `npm test` und `npx tsc` sind fahrbar), `tools/` (lesbar) |
| **Nicht** im Arbeitsort | `docs/`, `.serena/`, `dist/`, `android/`, `assets/`, `tools/privacy-scan.mjs`. Aussagen über diese sind hier nicht zu treffen. |

## Was zu tun ist

### 1 — Typen

- `Employment` (in `src/domain/employment.ts`) bekommt:
  - `id: string` — stabil, wird nie wiederverwendet
  - `name: string` — Anzeigename der Beschäftigung
  - `arbeitgeber: string`, `personalnummer: string`, `abteilung: string` — **neu hier**,
    denn sie sind je Arbeitsverhältnis verschieden.
    ★ **`Profile` behält diese drei Felder vorerst unverändert.** Sie dort zu entfernen
    würde in diesem Auftrag den PDF-Kopf (`src/pdf/report-pdf.ts`) und das
    Stammdatenformular (`src/ui/screens/MoreScreen.tsx`) mit aufreißen — beides gehört
    in AUF-005 und AUF-007. Die Migration **kopiert** die Werte; die doppelte Haltung
    ist ein bewusster Übergang, kein Versehen.
- `TimeEntry`, `VacationDay` und `RunningSession` bekommen je ein Pflichtfeld
  `employmentId: string`.

**ID-Vergabe, verbindlich:**
- Die Migration vergibt die feste ID `emp-1`. Fest, damit sie deterministisch
  prüfbar ist.
- Jede **neu angelegte** Beschäftigung bekommt
  `emp-${Date.now()}-${Math.random().toString(36).slice(2, 8)}`.
  **Nicht** `crypto.randomUUID` (in alten Android-WebViews nicht überall da) und
  **nicht** eine fortlaufende Nummer: eine gelöschte Nummer würde neu vergeben, und
  alte Einträge hingen plötzlich an der falschen Beschäftigung.

### 2 — Persistenz

- Neuer Preferences-Schlüssel `employments` trägt die **Liste**. Der alte Schlüssel
  `employment` bleibt liegen und wird **nicht gelöscht** — er ist der Rückweg, falls
  die Migration schiefgeht.
- Dexie in `src/db/db.ts` bekommt `version(2)` mit Index auf `employmentId` **und**
  einem `upgrade`-Hook, der jedem vorhandenen Eintrag `employmentId = 'emp-1'` setzt.
  Der DB-Name `'zeiterfassung'` bleibt unverändert (siehe `CLAUDE.md`, „Stabile
  Bezeichner").
- Die Urlaubsliste und die laufende Erfassung werden beim Lesen migriert: fehlt
  `employmentId`, gilt `emp-1`.

### 3 — Migration der Stammdaten

Beim ersten Lesen von `employments`:
1. Liegt die Liste schon vor → nichts tun.
2. Sonst: aus dem alten `employment`-Objekt **eine** Beschäftigung bilden, `id`
   `emp-1`, `name` aus `Profile.arbeitgeber` (leer → `"Beschäftigung 1"`), und
   `arbeitgeber`/`personalnummer`/`abteilung` aus dem Profil übernehmen.
3. Gibt es auch das alte Objekt nicht → Liste mit einer Beschäftigung aus
   `defaultEmployment`.

### 4 — Oberfläche nur so weit, dass es übersetzt

`npx tsc --noEmit` muss grün sein. Dafür darfst du in `src/ui/` genau so viel ändern,
wie der Übersetzer verlangt — die **erste** Beschäftigung der Liste gilt überall als
die aktive. **Keine** neuen Knöpfe, Auswahlfelder, Listen oder Beschriftungen. Wer hier
schon eine Auswahl baut, nimmt AUF-005 und AUF-006 vorweg und macht beide unprüfbar.

### 5 — Tests

Neue Tests, jeweils mit benanntem Testnamen:

| # | prüft |
|---|---|
| 1 | Migration ohne Altdaten → genau 1 Beschäftigung, `id === 'emp-1'` |
| 2 | Migration aus altem `employment` → Vertragswerte (Wochenstunden, Arbeitstage, Beginn, Anfangssaldo) unverändert übernommen |
| 3 | Migration übernimmt `arbeitgeber`/`personalnummer`/`abteilung` aus dem Profil |
| 4 | Liegt `employments` bereits vor, wird **nicht** erneut migriert |
| 5 | Dexie-Upgrade v1→v2: **alle** Bestandseinträge tragen danach `employmentId === 'emp-1'`, und ihre Anzahl ist vorher wie nachher gleich |
| 6 | Urlaubstag ohne `employmentId` wird beim Lesen `emp-1` zugeordnet |
| 7 | Neue IDs sind eindeutig: 100 Vergaben ergeben 100 verschiedene Werte |

Für Test 5 ist `fake-indexeddb` als devDependency vorhanden (`^6.2.5`) — benutze sie.

## Was ausdrücklich NICHT zu tun ist

- **`buildBalanceLedger`, `buildVacationStatus`, `monthSollMs`, `vacationOfMonth`,
  `dailyTargetMs` und `annualVacationDays` nicht anfassen.** Sie rechnen bereits für
  genau einen Vertrag und bekommen später nur gefilterte Eingaben. In `CLAUDE.md` steht
  unter „Zwei Deckel nicht verwechseln", warum an dieser Stelle schon einmal etwas
  schiefging.
- **Keine bestehende Erwartung in `src/domain/employment.test.ts` ändern.** Erlaubt ist
  ausschließlich, Testdaten um neue Pflichtfelder zu **ergänzen**. Nicht erlaubt: eine
  erwartete Zahl ändern, eine Assertion entfernen, einen Test löschen oder `.skip`
  setzen.
- **`Profile` in `src/domain/types.ts` nicht verändern** und `src/pdf/report-pdf.ts`
  nicht anfassen. Siehe Schritt 1: die drei Felder werden kopiert, nicht verschoben.
- Den DB-Namen `'zeiterfassung'` und die Backup-Kennung `app: 'zeiterfassung'` nicht
  umbenennen.
- `src/db/backup.ts` und `src/db/auto-backup.ts` **nicht** umbauen — das ist AUF-008.
  Nur so weit anfassen, wie der Übersetzer es verlangt.
- Nichts nachinstallieren, `package.json` nicht ändern.
- `tools/` nicht anfassen; `tools/privacy-scan.mjs` nicht lesen und nicht zitieren.

## Erwartung des Auftraggebers

> **Vor dem Lauf geschrieben.** Die Ausgangszahlen sind am 2026-09-22 im Hauptbaum
> gemessen: `npm test` → 1 Testdatei, 50 Tests, alle grün; `npx tsc --noEmit` → Exit 0.

1. **`npx tsc --noEmit` endet mit Exit 0.** Das ist die harte Schwelle: ohne sie ist
   der Rest gegenstandslos.
2. **`npm test` zählt mindestens 57 Tests** (die 50 bestehenden plus die 7 neuen) und
   **alle sind grün**. Weniger als 57 heißt, ein Fall aus der Tabelle fehlt.
3. **Die 50 bestehenden Tests sind inhaltlich unverändert.** Ich erwarte in
   `git diff src/domain/employment.test.ts` **nur** Zeilen, die ein Feld ergänzen —
   keine geänderte Zahl, keine entfernte Assertion.
4. **Die Negativkontrolle fällt um.** Nimm den `upgrade`-Hook in `src/db/db.ts`
   heraus, fahre Test 5, und er MUSS rot werden. Nenne den Testnamen und die
   Fehlermeldung wörtlich. Bleibt er grün, deckt er nichts ab, und Test 5 ist
   wertlos — das wäre der wichtigste Befund dieses Auftrags.
5. **Kein Eintrag geht verloren.** Test 5 zählt vorher und nachher; beide Zahlen
   stehen in der Lieferung.
6. Ich erwarte, dass du in `src/ui/` **zwischen 3 und 10 Zeilen** ändern musst, damit
   es übersetzt. Deutlich mehr heißt, dass du Oberfläche gebaut hast, die hier nicht
   hingehört; deutlich weniger heißt vermutlich, dass `employmentId` doch nicht
   Pflicht ist.

**Woran ich merke, dass die Erwartung falsch war:** wenn Punkt 4 nicht eintritt. Ein
Migrationstest, der auch ohne die Migration grün bleibt, meldet „abgedeckt", wo nichts
abgedeckt ist — und diese Migration läuft später über echte Arbeitszeitdaten.

## Lieferung

`auftraege/_ergebnisse/AUF-004_lieferung.json`, gebildet gegen `tools/lieferschema.json`.

- Achse `implementiert` für jede Codestelle (mit `quellbeleg`, Anker in der Zieldatei).
- Achse `getestet` **nur** für Stellen, zu denen du die Negativkontrolle gefahren hast.
  „Der Code steht" ist nicht „der Test fällt ohne ihn um".
- **Neu und hier wichtig:** ein Befehl, der absichtlich rot wird (die Negativkontrolle),
  trägt `erwarteter_exit: 1`. Ohne dieses Feld meldet die Abnahme ihn als Fehlschlag.
  Ein angekündigter Exit, der nicht eintritt, ist ebenfalls ein Befund — das Feld ist
  kein Freibrief.
- **Nullaussagen brauchen einen Befehl, der die Null AUSGIBT.** `git diff` mit leerer
  Ausgabe belegt keine 0; `git diff --numstat -- <datei> | Measure-Object -Line` tut es.
  (Gemessen an AUF-003: genau daran scheiterten dort zwei Befunde zu Recht.)
- `nicht_erreicht` ist Pflicht, auch wenn es leer bleibt.

### Achsen in diesem Auftrag

| Achse | wann | Beleg |
|---|---|---|
| `implementiert` | der Code steht | C1 (die Zeile, die es tut) oder C2 (Typdefinition) |
| `getestet` | ein Test fährt darüber UND fällt um, wenn man die Änderung zurückdreht | L1 mit Testnamen + die Negativkontrolle |
| `gemessen` | eine Zahl liegt vor, mit Positiv- und Negativkontrolle | L1/L2 + `ablage` |

### Anker

Ein wörtliches Stück, das in der Zieldatei **genau einmal** vorkommt, als `datei.ts:N`.
Ein nacktes `:N` wird abgewiesen. Testnamen taugen als Anker, wenn sie im Repo
eindeutig sind — wähle sie entsprechend.

## Kontrollen, die der Auftrag verlangt

- [ ] Positiv-Kontrolle: die 50 bestehenden Tests laufen grün.
- [ ] Negativ-Kontrolle: der ausgebaute `upgrade`-Hook macht Test 5 rot, namentlich.
- [ ] Jede Zahl steht neben dem Befehl, der sie erzeugt hat.
- [ ] Jede Aussage mit einem Vollständigkeitswort („alle Einträge", „kein Verlust")
      trägt eine `grundgesamtheit` mit Anzahl, Befehl und Wurzel.

```
python -u tools/abnahme.py auftraege/_ergebnisse/AUF-004_lieferung.json --befehle
```
