# AUF-015 — An Clockodo übertragen

## Auftrag

Ein Knopf je Beschäftigung überträgt deren offene und geänderte Einträge an Clockodo und löscht
dort, was in Klarzeit gelöscht wurde — ohne Doppelbuchungen, ohne halb übertragene Einträge, mit
sofortigem Abbruch bei Anmelde-, Netz- und Mengenfehlern.

## Warum das gebraucht wird

Letzter Baustein der Clockodo-Anbindung (User, 2026-09-25; nur Klarzeit → Clockodo). Vorhanden:
Zugang und Schlüssel (AUF-012), Auswahl je Eintrag (AUF-013), rein rechnerisch Abschnitte,
Payloads, Prüfsumme und Status sowie `createEntry`/`deleteClockodoEntry` (AUF-014). Es fehlt
der Ablauf. Er schreibt in die Zeiterfassung des Arbeitgebers — deshalb sind die Fehlerregeln
unten genau und je mit einem Test belegt.

## Was zu tun ist

### 1 — Gerüst, Tests, Ausgangslauf — VOR der Umsetzung

   Ausgangslauf**, er steht in der Lieferung.

### 2 — Bausteine

**`src/db/clockodo-deletes.ts`** — Löschvermerke je Beschäftigung, Preferences-Schlüssel
`clockodoDeletes:<employmentId>` (Array von Clockodo-IDs, nicht im Backup):
`getClockodoDeletes(employmentId): Promise<number[]>` (fehlt/kaputt → `[]`),
`addClockodoDeletes(employmentId, ids)` (ohne Doppelte, Reihenfolge erhalten),
`removeClockodoDelete(employmentId, id)`.

**`src/db/entries.ts`:**
- `setEntryClockodoSync(id: number, sync: ClockodoSync | null)`: setzt den Stand; bei `null`
  wird das Feld **entfernt** (Dexie 4.4.3: `update(id, { clockodoSync: undefined })` löscht den
  Schlüssel, im Quelltext `setByKeyPath` → `delete obj[keyPath]`). **`updatedAt` bleibt
  unverändert** — das Setzen des Übertragungsstands ist keine Bearbeitung durch den Nutzer.
- `deleteEntryWithClockodo(entry: TimeEntry)`: löscht den Eintrag; hatte er `clockodoSync`,
  werden dessen `ids` für `entry.employmentId` vermerkt.

**`src/clockodo/transfer.ts`:**

```ts
export interface TransferResult {
  sent: number;     // Eintraege vollstaendig uebertragen (neu oder geaendert)
  deleted: number;  // in Clockodo geloeschte Eintraege (Vermerke + alte Abschnitte)
  skipped: { beforeStart: number; untimedBreak: number; incomplete: number };
  errors: { entryId?: number; clockodoId?: number; message: string }[];
  stopped: string | null; // Grund, falls der ganze Lauf abgebrochen wurde
}
export function transferEmployment(
  employmentId: string,
  opts?: { http?: ClockodoHttp; now?: () => number },
): Promise<TransferResult>;
```

Ablauf, **genau so**:
1. **Zugang.** Beschäftigung ohne `clockodo` → `stopped: 'Clockodo ist fuer diese
   Beschaeftigung nicht eingeschaltet.'`; `apiUser` leer → `'Clockodo-Login fehlt.'`; kein
   Schlüssel (`getClockodoKey`) → `'API-Schluessel fehlt.'`. In allen drei Fällen **keine
   einzige Anfrage**.
2. **Löschvermerke** in gespeicherter Reihenfolge: `deleteClockodoEntry`; Erfolg → sofort
   `removeClockodoDelete`, `deleted++`; Fehler → siehe Regel 5, bei Einzelfehler
   `errors.push({ clockodoId, message })`, die ID bleibt vermerkt.
3. **Einträge** der Beschäftigung aufsteigend nach `start`, Status per `transferStatus`:
   - `before-start` / `untimed-break` / `incomplete` → nur zählen (`skipped`), nichts senden;
   - `synced` → nichts;
   - `changed` → die alten IDs aus `clockodoSync.ids` **einzeln** löschen; nach **jedem**
     Erfolg die ID aus dem Stand entfernen (`setEntryClockodoSync` mit den restlichen IDs,
     gleicher Hash; keine IDs mehr → `null`), `deleted++`. Scheitert ein Löschen → Fehler,
     **kein** Neu-Senden dieses Eintrags, weiter mit dem nächsten. Sind alle gelöscht → wie
     `pending`;
   - `pending` → je Payload aus `buildEntryPayloads(entry, entry.clockodo, config.billable)`
     `createEntry`, IDs sammeln. Scheitert ein Abschnitt → die in diesem Lauf schon angelegten
     Abschnitte dieses Eintrags **wieder löschen** (Fehler dabei still), Eintrag bleibt ohne
     Stand, Fehler melden. Alle angelegt → `setEntryClockodoSync(id, { ids, hash:
     entrySyncHash(entry, entry.clockodo, config.billable), at: now() })`, `sent++`.
4. Anfragen **strikt nacheinander**, keine Parallelität.
5. **Fehlerregel:** `ClockodoError` mit `kind` `auth`, `network` oder `rate` beendet **den ganzen
   Lauf** sofort (`stopped` = Meldung des Fehlers; bis dahin Erledigtes bleibt gespeichert).
   Jede andere Art (`validation`, `forbidden`, `server`, `format`) betrifft nur den Eintrag bzw.
   den Vermerk (`errors`), der Lauf geht weiter.

### 3 — Oberfläche (`src/ui/screens/EntriesScreen.tsx`)

- Je Beschäftigung **mit** `clockodo` eine Karte über der Liste:
  `Clockodo – <Name>: <n> offen · <n> Pause ohne Uhrzeit · <n> ohne Auswahl` (offen = `pending`
  + `changed`) und Knopf **„An Clockodo uebertragen"**. Während des Laufs gesperrt; außerhalb
  der nativen App gesperrt mit Hinweis „nur in der Android-App". Danach das Ergebnis:
  `<n> uebertragen, <n> in Clockodo geloescht.`, jeder Fehler mit Datum/Uhrzeit des Eintrags
  (`formatDateTime`) bzw. `Clockodo-Eintrag <id>`, bei Abbruch `Abgebrochen: <Grund>`.
- Je Eintrag einer solchen Beschäftigung ein kurzer Stand: `synced` → `in Clockodo`,
  `changed` → `geaendert`, `pending` → `noch nicht uebertragen`, `untimed-break` →
  `Pause ohne Uhrzeit`, `incomplete` → `Clockodo-Auswahl fehlt`; sonst nichts.
- Löschen: immer über `deleteEntryWithClockodo`. Ist der Eintrag übertragen, sagt die Rückfrage
  zusätzlich: `Er wird beim naechsten Uebertragen auch in Clockodo geloescht.`
- „Alle Eintraege loeschen" (MoreScreen) und das Ersetzen per Backup **vermerken nichts** — sie
  wirken nur lokal. Nicht anfassen.
- Schreibweise der Datei (ASCII-Umschrift) übernehmen.
