# AUF-019 — Bausteine für Urlaubsanträge an Clockodo (Modell, Zeiträume, Client)

## Auftrag

Die Bausteine, aus denen AUF-020 (Ablauf) und AUF-021 (Oberfläche) die Urlaubsanträge an
Clockodo zusammensetzen: ein Urlaubstag kann sich seinen Clockodo-Antrag merken, offene Urlaubstage
werden zu Antragszeiträumen gebündelt, und der Client kann Abwesenheiten anlegen und lesen.
**Kein Ablauf, keine Oberfläche.**

## Warum das gebraucht wird

Der Nutzer will Urlaub aus Klarzeit in Clockodo beantragen und den Stand (beantragt, genehmigt,
abgelehnt) zurücklesen. Entscheidungen des Nutzers vom 2026-10-01: beantragen **und** Status
zurücklesen; beantragt werden Tage ab „Übertragen ab" (`syncFrom`), wie bei den Zeiteinträgen;
ein abgelehnter Tag bleibt in Klarzeit und wird nur markiert.

Primärquelle ist `https://docs.clockodo.com/openapi.yaml` (info.version `2026-09-23`):
`POST /v4/absences` (Pflicht `date_since`, `type`; dazu `date_until`, `status`, `users_id`),
`GET /v4/absences` mit `filter[users_id]`, `filter[year]`, `filter[type]`, Antwort `{ data: [...] }`.
Typ `1` = „Holiday from the quota". Status `0` Enquired (beantragt), `1` Approved, `2` Declined,
`3` ApprovalCancelled, `4` Cancelled. `date_until` muss im Jahr von `date_since` liegen
(`UntilMustBeInSameYearError`). Fehler kommen in zwei Formen: allgemein
`{ errors: [{ type, message }] }`, bei Abwesenheiten (422) `{ errors: [{ error: { type, … } }] }`;
Typen u. a. `AbsenceCollision`, `StatusIsForbidden`, `CannotManageAbsencesOfUser`. 409 heißt laut
Spec „A resource with the data already exists".

### 3 — Umsetzung

- `toDateInput`: `format(epoch, 'yyyy-MM-dd')` (`format` ist in `time.ts` schon importiert).
- `isClockodoAbsenceStatus`: ganze Zahl von 0 bis 4. `cleanClockodoAbsenceRef`: Objekt nötig; `id`
  über das vorhandene `positiveInt`; `status` über `isClockodoAbsenceStatus`; `at` endliche Zahl;
  sonst `null`.
- `cleanVacationDays` (`src/db/employment.ts`): Ein gültiger Verweis (`cleanClockodoAbsenceRef`)
  wird als `clockodoAbsence` mitgetragen; fehlt er oder ist er kaputt, **fehlt der Schlüssel ganz**
  (nicht `undefined`, nicht `null`). Die übrigen Regeln (Doppelprüfung, Rückfall `emp-1`,
  Sortierung) bleiben. `src/db/backup.ts` bleibt unverändert — der Verweis reist über
  `cleanVacationDays` mit.
- `vacationRequestRanges` (`src/domain/clockodo-absence.ts`), Doku-Kommentar mit diesen Regeln:
  - `emp.clockodo === null` → `[]`.
  - Offen ist ein Tag mit `employmentId === emp.id`, **ohne** `clockodoAbsence` und mit
    `date >= emp.clockodo.syncFrom`; aufsteigend sortiert.
  - Zwei aufeinanderfolgende offene Tage gehören in **denselben** Zeitraum, wenn sie im selben
    Kalenderjahr liegen **und** zwischen ihnen kein Arbeitstag liegt — gemessen mit dem vorhandenen
    `workdaysInRange(Tag danach, Tag davor, emp.workdaysPerWeek)` (Sonntag nie Arbeitstag, Samstag
    erst ab sechs Arbeitstagen). Der Jahresschnitt, weil Clockodo `date_until` im Jahr von
    `date_since` verlangt.
  - `dateSince`/`dateUntil` über `toDateInput`, `dates` aufsteigend.
- `src/clockodo/client.ts`:
  - Konstanten für Typ 1 („Holiday from the quota") und Status 0 (beantragt) mit Kommentar.
  - Einlesen einer Abwesenheit: `id` ganze positive Zahl; `date_since`/`date_until` Text im Muster
    `yyyy-MM-dd`; `status` über `isClockodoAbsenceStatus`; `count_days` endliche Zahl, sonst `null`.
  - Fehlertypen aus **beiden** Fehlerformen lesen (`errors[].type` und `errors[].error.type`);
    eine Text-Antwort, die kein JSON ist, ergibt keine Typen (kein Wurf).
  - Fehlerregel für Abwesenheiten — **erst der Status, dann die Form** (Lehre aus AUF-014):
    2xx → kein Fehler; was `mapStatus` als `auth` oder `rate` meldet, bleibt so; Status 409 **oder**
    Typ `AbsenceCollision` → `collision` („Der Zeitraum ueberschneidet sich mit einer Abwesenheit
    in Clockodo."); Typ `StatusIsForbidden` oder `CannotManageAbsencesOfUser` → `forbidden`
    („Clockodo laesst einen Urlaubsantrag fuer diesen Zugang nicht zu."); Typ
    `UntilMustBeInSameYear` → `validation` („Ein Urlaubsantrag darf nicht ueber den Jahreswechsel
    gehen."); sonst das Ergebnis von `mapStatus`. Status jeweils mitgeben.
  - `createAbsence`: `POST /v4/absences` über das vorhandene `clockodoRequest`, Rumpf **genau**
    `{ users_id, date_since, date_until, type: 1, status: 0 }` — `users_id` ausdrücklich (die Spec
    sagt nicht, was ein fehlendes bedeutet), `status: 0` ausdrücklich (ohne Status wüsste niemand,
    ob Clockodo einen Antrag oder eine fertige Abwesenheit anlegt). Fehlerregel vor dem Einlesen;
    Antwort `{ data: <Abwesenheit> }`, sonst `format`.
  - `fetchAbsences`: `GET /v4/absences` über das vorhandene `clockodoGet` mit genau den Parametern
    `filter[users_id]`, `filter[year]`, `filter[type]` = `'1'` (als Text). `data` muss eine Liste
    sein, **jeder** Eintrag muss sich einlesen lassen — ein kaputter Eintrag ist `format`, kein
    stilles Überspringen (der Ablauf entscheidet auf dieser Liste, ob er sendet).
