# AUF-012 — Clockodo-Zugang je Beschäftigung

## Auftrag

Eine Beschäftigung lässt sich mit einem Clockodo-Konto verbinden: Login-E-Mail und API-Schlüssel
eintragen, Verbindung testen, Kunden, Projekte und Leistungen laden und Vorgaben wählen — der
Schlüssel liegt verschlüsselt auf dem Gerät und nie in einem Backup.

## Warum das gebraucht wird

Der User will Einträge an die Clockodo-Zeiterfassung seiner Firma übertragen (2026-09-25, nur
Klarzeit → Clockodo). Dieser Auftrag baut den **Zugang**; übertragen wird noch nichts (späterer
Auftrag). Ein Lesetest des Users am 2026-09-25 hat gezeigt: Anmeldung per E-Mail und Schlüssel
funktioniert, das Konto darf alle Leistungen, Kunden und Projekte buchen, und es gibt über 100
Projekte (eine Seite zu 100 war voll).

## Primärquelle

`https://docs.clockodo.com/openapi.yaml` (info.version 2026-09-23), wörtlich geprüft:
- Basis `https://my.clockodo.com/api`.
- Header `X-ClockodoApiUser: [email address]`, `X-ClockodoApiKey: [API key]` und — bei diesem
  Verfahren Pflicht — `X-Clockodo-External-Application: [name of application or company];[email address]`.
- `GET /v4/users/me` → `{ data: { id, name, … } }`.
- `GET /v3/customers`, `GET /v4/projects`, `GET /v4/services` → `{ data: [...], paging: { count_items,
  count_pages, current_page, items_per_page } }`; Parameter `items_per_page` (1–5000) und `page`.
  Jedes Element hat `id`, `name`, `active`; Projekte zusätzlich `customers_id`.
- Statuscodes: 401 Anmeldung, 403 Rechte, 400/422 Validierung, 429 zu viele Anfragen.
- `billable` beim späteren Anlegen: `0` nicht abrechenbar, `1` abrechenbar.

Android, `https://developer.android.com/identity/data/autobackup`: „If you specify an `<include>`
element, the system no longer includes any files by default" — ein Regelwerk **nur** mit
`<exclude>` lässt die übrige Sicherung unangetastet. Beispiel der Seite:
`<exclude domain="sharedpref" path="device.xml"/>`. Attribute: `android:fullBackupContent` (bis
Android 11), `android:dataExtractionRules` mit `<cloud-backup>` und `<device-transfer>` (ab 12).

Plugin `capacitor-secure-storage-plugin` 0.13.0 (vom Auftraggeber installiert, in `package.json`):
`SecureStoragePlugin.get({ key }) → { value }`, `.set({ key, value })`, `.remove({ key })`; `get`
und `remove` werfen bei fehlendem Schlüssel `'Item with given key does not exist'`. Android legt
die Werte in der SharedPreferences-Datei `cap_sec` ab (Quelltext: `PREFERENCES_FILE = "cap_sec"`).

### 2 — Module

**`src/domain/clockodo.ts`** (rein):

```ts
export interface ClockodoConfig {
  apiUser: string;                   // Login-E-Mail (Header X-ClockodoApiUser); darf leer sein
  syncFrom: number;                  // uebertragen ab diesem Tag (epoch ms, lokale Mitternacht)
  defaultCustomersId: number | null; // Vorgaben fuer neue Eintraege
  defaultProjectsId: number | null;
  defaultServicesId: number | null;
  billable: 0 | 1 | null;            // null = nicht mitsenden
}
export interface ClockodoLists {
  fetchedAt: number;
  customers: { id: number; name: string }[];
  projects: { id: number; name: string; customersId: number }[];
  services: { id: number; name: string }[];
}
export function cleanClockodoConfig(raw: unknown): ClockodoConfig | null;
```

`cleanClockodoConfig`: kein Objekt → `null`; `syncFrom` keine endliche Zahl → `null`; `apiUser`
Text → getrimmt, sonst `''`; jede ID nur als positive Ganzzahl, sonst `null`; `billable` nur `0`
oder `1`, sonst `null`. Ein leeres `apiUser` ist erlaubt — sonst ginge ein frisch eingeschalteter
Zugang beim ersten Speichern verloren. Einen API-Schlüssel kennt dieser Typ **nicht**.

**`Employment.clockodo: ClockodoConfig | null`** (`src/domain/employment.ts`) — Pflichtfeld im Typ,
`null` = keine Übertragung; `defaultEmployment.clockodo = null`. `cleanEmployment`
(`src/db/employment.ts`) setzt `clockodo: cleanClockodoConfig(x.clockodo)`.

**`src/clockodo/client.ts`:**

```ts
export const CLOCKODO_API = 'https://my.clockodo.com/api';
export interface ClockodoAuth { apiUser: string; apiKey: string }
export interface ClockodoRequest { method: 'GET'; url: string; headers: Record<string, string>; params?: Record<string, string> }
export type ClockodoHttp = (req: ClockodoRequest) => Promise<{ status: number; data: unknown }>;
export type ClockodoErrorKind = 'auth' | 'forbidden' | 'rate' | 'validation' | 'server' | 'network' | 'format';
export class ClockodoError extends Error { readonly kind: ClockodoErrorKind; readonly status?: number }
export function clockodoHeaders(auth: ClockodoAuth): Record<string, string>;
export function fetchMe(auth: ClockodoAuth, http?: ClockodoHttp): Promise<{ id: number; name: string }>;
export function fetchLists(auth: ClockodoAuth, http?: ClockodoHttp, now?: number): Promise<ClockodoLists>;
```

- `clockodoHeaders` liefert **genau** `X-ClockodoApiUser`, `X-ClockodoApiKey`,
  `X-Clockodo-External-Application: Klarzeit;<apiUser>`, `Accept: application/json`.
- Standard-`http` ist `CapacitorHttp.request` (wie im Updater, wegen CORS). Außerhalb der
  nativen App wirft es `ClockodoError('network', 'Clockodo ist nur in der Android-App erreichbar.')`.
  `data` kann Text sein → `JSON.parse`.
- Fehler: Ausnahme von `http` → `network` `'Keine Verbindung zu Clockodo.'`; 401 → `auth`
  `'Anmeldung bei Clockodo fehlgeschlagen: E-Mail oder API-Schluessel pruefen.'`; 403 →
  `forbidden` `'Keine Berechtigung bei Clockodo.'`; 429 → `rate`
  `'Zu viele Anfragen an Clockodo, bitte spaeter erneut versuchen.'`; 400/422 → `validation`
  `'Clockodo hat die Anfrage abgelehnt (Status <n>).'`; jeder andere Status außerhalb 200–299 →
  `server` `'Clockodo meldet einen Fehler (Status <n>).'`; unerwartete Form → `format`
  `'Unerwartete Antwort von Clockodo.'`. **Keine Meldung enthält je den Schlüssel.**
- `fetchMe`: `GET ${CLOCKODO_API}/v4/users/me`, liefert `{ id, name }` aus `data`.
- `fetchLists`: nacheinander `/v3/customers`, `/v4/projects`, `/v4/services`, je mit
  `params: { items_per_page: '1000', page: '<n>' }` für `n = 1 … paging.count_pages` (fehlt
  `paging`: nur Seite 1). Übernommen werden nur Elemente mit `active === true`, ganzzahliger `id`
  und Text-`name`; Projekte mit `customersId` aus `customers_id`. Jede Liste nach `name`
  sortiert (`localeCompare(…, 'de')`). `fetchedAt = now` (Vorgabe `Date.now()`).

**`src/clockodo/key-store.ts`:** `getClockodoKey(employmentId): Promise<string | null>` (fehlt →
`null`, Ausnahme des Plugins abgefangen), `setClockodoKey(employmentId, key)`,
`removeClockodoKey(employmentId)` (fehlt → still). Plugin-Schlüssel `clockodo-key-<employmentId>`.
Nie Preferences, nie `Employment`, nie Backup, nie eine Meldung.

**`src/db/clockodo-lists.ts`:** Preferences-Schlüssel `clockodoLists:<employmentId>`;
`getClockodoLists(employmentId): Promise<ClockodoLists | null>` (fehlt oder kein gültiges JSON mit
`fetchedAt` als Zahl und drei Arrays → `null`), `saveClockodoLists(employmentId, lists)`,
`removeClockodoLists(employmentId)`. Gehört **nicht** ins Backup (jederzeit neu ladbar).

### 3 — Oberfläche und Android

**`ClockodoSettings.tsx`** — Props `{ employmentId: string; value: ClockodoConfig | null;
onChange: (next: ClockodoConfig | null) => void }`, eingebunden in „Beschaeftigung bearbeiten"
(`MoreScreen.tsx`) über `setEmpField('clockodo', …)`, vor den Knöpfen des Formulars:
- Schalter „An Clockodo uebertragen". **Ein** → `onChange` mit `apiUser: ''`, `syncFrom` = heute
  0:00 Uhr lokal, alle Vorgaben `null`. **Aus** → `onChange(null)` **und** `removeClockodoKey` sowie
  `removeClockodoLists` — es bleibt kein Zugang auf dem Gerät zurück.
- „Clockodo-Login (E-Mail)", „Uebertragen ab" (`<input type="date">`, `fromDateInput`).
- Schlüssel: Passwortfeld mit eigenem Knopf „Schluessel speichern" (`setClockodoKey`); danach wird
  das Feld geleert und „Schluessel gespeichert" angezeigt. Ein gespeicherter Schlüssel wird **nie**
  angezeigt, nur ob einer da ist.
- „Verbindung testen": `fetchMe` mit E-Mail + gespeichertem Schlüssel → „Verbunden als <Name>",
  danach `fetchLists` → `saveClockodoLists` → „<n> Kunden, <n> Projekte, <n> Leistungen geladen".
  Fehler: die Meldung von `ClockodoError`.
- Vorgaben aus dem Zwischenspeicher: Kunde, Projekt (nur die des gewählten Kunden, plus „kein
  Projekt"), Leistung, „Abrechenbar" (nicht mitsenden / nicht abrechenbar / abrechenbar).
- Außerhalb der nativen App statt des Testknopfs der Hinweis, dass Clockodo nur in der Android-App
  erreichbar ist.

**`MoreScreen.tsx`:** beim Löschen einer Beschäftigung auch `removeClockodoKey` und
`removeClockodoLists`. Abschnitt „Datenschutz" wahr halten — ergänzen, sinngemäß: *Ausnahme:
Schaltest du bei einer Beschaeftigung die Uebertragung an Clockodo ein, verbindet sich die App mit
deinem Clockodo-Konto und uebertraegt die Eintraege dieser Beschaeftigung (Zeiten, Pausen als
Luecken, Taetigkeit, Kunde, Projekt, Leistung). Der API-Schluessel liegt verschluesselt auf dem
Geraet und steht in keinem Backup.* Schreibweise der Datei (ASCII-Umschrift) übernehmen.

**Android:** `res/xml/backup_rules.xml` (`<full-backup-content>`) und
`res/xml/data_extraction_rules.xml` (`<data-extraction-rules>` mit `<cloud-backup>` und
`<device-transfer>`), jeweils **nur** `<exclude domain="sharedpref" path="cap_sec.xml"/>`. Im
Manifest an `<application>`: `android:fullBackupContent="@xml/backup_rules"` und
`android:dataExtractionRules="@xml/data_extraction_rules"`. `android:allowBackup` bleibt `true`.

## Was ausdrücklich NICHT zu tun ist

- ⛔ **`isValidEntry` in `src/db/backup.ts` nicht anfassen** (CLAUDE.md, ⛔-Absatz).
- **Nichts an Clockodo schreiben**, keine Einträge übertragen, keine Auswahl je Eintrag — spätere
  Aufträge. Kein `POST`, `PUT` oder `DELETE` im Client.
- Kein echter Netzaufruf in Tests, kein echter Schlüssel, keine echten Namen oder IDs.
- Backup-`version` bleibt 3, Kennung `app: 'zeiterfassung'` und DB-Name bleiben; keine neue
  Dexie-Version.
- `android:allowBackup` nicht ändern; in den Regeln **kein** `<include>`.
- Keine Testing-Library, kein weiteres Paket, `package.json` nicht ändern. `tools/` nicht anfassen.
  Nicht committen.
- Bestehende Tests nicht in ihren Erwartungen ändern. Baut ein bestehender Test ein `Employment`
  von Hand und kompiliert nicht mehr, bekommt er `clockodo: null` — sonst nichts.
- Hilfsskripte in reinem Python (`pathlib`, `re`; `subprocess` nur für `npx`). Keine
  Fremdprogramme wie `rg`/`grep` per `subprocess`. Ein Skript, das eine Kontrolle fährt, prüft
  die erwarteten roten Tests **selbst** und endet nur dann mit 0, wenn sie stimmen — der Exit des
  Schlusslaufs allein belegt nichts (AUF-011).
